# 架构与取舍

## 目标

维护一个可随需要扩充的个人扩展合集，减少多个独立插件带来的维护和分发负担。一个仓库、一个 Paseo 安装项、一个整体发布版本。

这里的「子功能」是源代码组织单位，不是能独立安装的 Paseo 插件。壳不定义新的功能实现协议；组合对象就是 Paseo 原生贡献函数和原生设置页面描述符。

## 静态组合

```text
features/<id>/{feature.json,client,server,shared}
shell/{client,server,shared}
          │ npm run build
          ├── 校验元信息、入口、原生类型与源码依赖边界
          ├── 内存中的静态 imports、展示信息和原生贡献表
          ├── client/bundle.js ← index.client.tsx
          └── server/bundle.js ← index.server.ts

服务端 bundle → registerSettings → 读取开关一次 → 启动已选服务端贡献
                                      │
                                启动快照 RPC
                                      │
客户端 bundle → 注册管理/配置页 → 读取快照一次 → 启动对应客户端贡献
```

采用**功能优先的手写源码、运行端优先的构建产物**。功能只在 `features/<id>/` 内维护，壳代码在 `shell/`。统一构建稳定排序扫描功能，把明确的静态 import 和六项元信息放入内存入口，直接输出两端 bundle；不创建需要同步提交的接线文件。shared 按需打入两端，没有第三份强制产物。

Paseo v0.15.4 的编译器只认可插件根的 `client/`、`server/`、`shared/` 与两个原生入口，不能直接消费 `features/` 或 `shell/`。固定原生入口各自只重导出本端 bundle，宿主只看到运行目录内的产物。这是普通打包，不通过 alias、软链接、转发源码或伪装依赖绕过宿主边界。

`client/`、`server/` 完全由构建工具管理，产物及其原生类型声明均忽略提交；不要在这些目录写源码。SDK、React、React Native、TanStack Query 和 Zod 等 0.15.4 宿主库保持 external，普通第三方库随本端打包。运行时没有扫描、远程发现、动态注入或任意功能模块加载器，功能与壳整体分发。

源码归属由构建工具在打包前严格检查：包含 type-only、类型查询、再导出、类型引用和传递依赖。每个功能及壳内部均遵循本端/shared 规则；功能不得依赖其他功能或壳内部实现，运行代码不得依赖测试/fixtures 或仓库根 `tools/`，但本端业务 `tools/` 子目录可以正常使用。shared 不依赖 Node、React 或端专用 SDK。shared 的第三方实现图另作共享归属检查，不能通过打包擦除导入来绕过。宿主实际消费的入口图和 external 还要在打包后再检查。

功能的运行期模块不得在顶层做文件写入、注册、启动计时器等副作用。静态导入会评估所有模块，包括关闭功能；行为应放在原生贡献函数内。这属于可关闭模块的必要语义，不要求任何特定业务架构。

## 开关与重载

壳使用原生 `defineSettings`，文档 ID 为 `zeonest-shell`，版本 1：

```json
{ "enabled": { "feature-id": true } }
```

不存在的开关默认关闭。未知或已移除的功能 ID 不会运行，也不会在保存其他开关时被强制删除；以后恢复同 ID 功能会继承原来的开关，因此不要把旧 ID 用于无关功能。

每次服务端启动只读取一次设置。客户端使用该次服务端启动快照，而不是重新读取最新开关来决定启动内容。这避免在「保存但尚未重载」时新连接的客户端提前运行功能。

开关保存是 Paseo 原生带 revision 的完整文档写入；冲突或连接错误不会显示为成功，用户可重新读取后重试。保存成功后管理页显示待生效数量。配置页提供「重新加载插件」，调用服务端 RPC，通过宿主 PATH 中的 `paseo plugin reload zeonest` 应用变更；宿主原生插件菜单仍可使用，不操作或重启 daemon。

0.15.4 的插件公开 SDK 没有重载接口，因此服务端用明确的 `--home` 选择继承的 `PASEO_HOME`（默认 `~/.paseo`），并先以 CLI 查询状态，确认 `workerPid` 等于插件父进程 ID。核对失败不会执行重载。重载命令脱离插件进程运行，同一进程中的并发请求合并；cleanup 只取消执行前检查，不等待或终止已发出的重载，避免自重载死锁。CLI 超时、执行错误和连接中断会提示检查插件状态，不将请求中断视为成功。

所有连接客户端统一使用同一份服务端选项；重载前后现有 agent session 的刷新行为仍由 Paseo 原生机制决定。本项目不额外重载 agent 或中断正在执行的轮次。

## 配置所有权

- 外壳只持有启停开关，不建立子功能统一配置 schema。
- 每个子功能可使用 Paseo 原生 settings、自己的 RPC、文件或其他适合的实现。
- 可选配置页面和支撑配置的服务端注册始终存在，便于启用前配置。
- 始终运行的配置注册只用于配置，不承载关闭后还会发生的业务行为。
- 配置生效方式由子功能说明，不强制与壳开关相同。
- 原生 host settings 是普通 JSON，不是凭据保险箱；敏感凭据由子功能选择合适的服务端存储。

## 生命周期与失败

外壳保存原生贡献函数返回的 cleanup，在整个插件停止时倒序执行，继续执行其余 cleanup 后汇总错误。延迟的开关读取或 RPC 在 teardown 后不会再启动子功能。

设置读取失败、数据无效、服务端或客户端贡献启动失败，会在管理页显示错误并记录日志，不把未知状态标成正常运行。配置管理页面本身不依赖业务功能成功启动。无效设置不会静默丢弃，用户可显式重置壳的开关。

这是一个**共享信任域**，不是子功能隔离系统。启动函数若在返回 cleanup 之前失败，已创建的部分原生注册或资源可能需要整体重载才能释放；子功能应在自己的初始化失败路径释放其资源。壳不承诺单个子功能崩溃隔离或事务式热回滚。

## 内部文件与非目标

`shell/shared/lifetime.ts`、`shell/shared/runtime.ts` 和 `shell/client/runtime-store.ts` 是壳的实现细节。子功能不依赖它们。没有额外对外 SDK。

不实现动态装载、依赖注入、沙箱、子功能依赖图、配置 schema 生成器、独立包管理、自动安装和自动更新。需要新的能力时先在子功能内部实现，不以未来扩展为由扩大壳的职责。
