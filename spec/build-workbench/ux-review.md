# 构建工作台：现状调查与交互提案

调查基线：`feature/build-workbench-tab` 的 `c685d4e`。本轮只做调查和原型，未改动插件、运行协议或项目配置。用本分支 `Workbench` 在隔离副本重跑了两个项目；布局问题以用户反馈和本分支界面源码为依据。本机 Paseo 0.16.2 加载的是另一份 Zeonest checkout，本轮未重载，因此没有把原型或源码检查当成真实宿主的视觉验收。

### 隔离验证结果

- **vofa_bridge**：用 `fedf599` checkout 的当前工作文件（包括已有未提交的 CMake 修订），排除原 `.zeonest-build/`，没有使用干净提交版本或现成构建目录。CMake 4.5.1，以 `Release` 和本机 `fmt` 路径配置，返回 `退出码 0；刷新目标以读取 File API`。再调用 `discover()` 返回 `configure`、`example`、`player`。以默认构建选项分别构建后两项，均退出码 0，均报告新产物；未执行二进制。
- **alkaa**：用 `8524e062` 的 Git 快照，复制本机 Wrapper/依赖缓存到独立 `GRADLE_USER_HOME`，使用现有 Android SDK。`tools()` 无保存项；此进程 `JAVA_HOME` 指向 mise 的 Zulu 8，候选排序把它放在首位，客户端会选择这一项。`verify()` 只确认 `openjdk version "1.8.0_514"` 能启动；`tasks --all --offline` 退出码 1，报告 `Gradle requires JVM 17 or later to run. Your build is currently configured to use JVM 8.` 手动选已有 Temurin 17.0.21.1 后，同一探测成功，达到 256 个任务的保留上限；重新发现确认有 `:app:assembleDebug` 和 `:desktop-app:createDistributable`。未跑构建任务，没有修改项目、全局 JDK 或 daemon 设置。

[Gradle 9.5.1 官方兼容矩阵](https://docs.gradle.org/9.5.1/userguide/compatibility.html#java_runtime) 区分了启动 Wrapper 客户端的 Java 与运行 Gradle 的 JVM：前者支持 JVM 8，后者要求 JVM 17–26。由此不能推出每个项目的 JDK 都应换成 17。若项目有独立 daemon JVM 声明、`org.gradle.java.home`，或 Wrapper 版本/来源不能确认，应保留并提示这些边界。满足 Gradle 已知范围也不同于已验证 Android 插件、SDK 和构建配置。

## 原型走查

在浏览器打开 [`prototype/index.html`](prototype/index.html) 即可，无需安装依赖。页面中的检查、探测、构建、日志和文件均为模拟，不读取项目，也不执行命令。

1. **hello-rust · Cargo**：目标来自 `Cargo.toml`，示例工具链已检查，直接点「构建目标」。第一次留空使用默认参数，第二次在「常用选项」勾选 `--release`，点「应用选项」后构建。左侧最新记录在最上方；在右侧选「产物」后切换左侧记录，可对照 `target/release/hello-rust` 和 `target/debug/hello-rust`。
2. **vofa_bridge**：选 `configure`，在「常用选项」勾选 Release 和 fmt 路径，再检查 CMake 并执行探测。左侧自动出现 `example` 和 `player`；顶部的「查看新目标」只定位列表。选中目标后手动构建。也可以输入 `--preset missing` 模拟配置失败，再从左侧选失败记录查看右侧输出。
3. **alkaa**：先看为何 Zulu 8 不适用。手动选择并检查 Temurin 17，从「常用选项」插入 `--offline` 后执行探测；试搜 `assembleDebug` 或浏览长任务列表。选中任务后核对命令、工具与工作目录，再确认构建。这个案例的探测上下文只供一次启动，下一次构建前会提示重新探测。
4. 在「常用选项」里可以一次选多项。应用后追加在已有命令选项末尾；取消不改动当前草稿。
5. 切到「输出」，展开默认折叠的「命令预览」核对这一轮的命令与工作目录。日志默认跟随底部；向上滚动后，新行不会把视图拉回底部。点击「回到底部」即可恢复跟随。
6. 拖动运行区顶部的横线调整高度。也可以聚焦横线后用 `↑` / `↓` 调整，按住 `Shift` 加大步幅，按 `Home` / `End` 切到最小或最大高度。缩窄窗口后，检查历史和详情是否仍能同时查看。

浏览器走查覆盖 1400 × 850、390 × 740 和 320 × 630，查看了明暗配色、Cargo 两次构建的记录排序与详情切换、拖拽和键盘调高、CMake 失败与目标刷新、Gradle 确认流程。窗口变矮时检查了高度限制。这些是原型结果，真实 Paseo 面板仍待实现后验证。

参考 JetBrains 的[停靠工具窗口](https://www.jetbrains.com/help/idea/manipulating-the-tool-windows.html)和[运行配置与 Run widget](https://www.jetbrains.com/help/idea/run-debug-configuration.html)。借用分区和固定操作的位置；不把 IDE 的整套路由或可拆分窗口搬进 Paseo。原型用可切换的亮、暗配色；正式实现用宿主主题和工作区面板实际可用的宽度。

## 实施前要对齐的两点

- **布局**：宽屏右侧工具链常驻，compact 把工具链作为相邻页签。底部左侧常驻记录，从新到旧排列；新运行开始时选中该记录并展示输出，手动切换记录时保留右侧当前的「输出」或「产物」页签。底部高度由分隔线调整，留出上方配置的操作空间。
- **推进方式**：建议探测完成自动刷新，有新目标时把「查看新目标」作为下一步，但不替用户选目标或开始构建。已验证工具在同一适用范围复用；未验证工具仍显式检查，确定不兼容时引导选择，不静默换 JDK。

确认后再修改产品。实现验收需覆盖成功/失败的探测、无新目标、截断、切换工作区、保留未保存草稿和工具消失；自动刷新失败时保留上次结果和重试入口。用真实 Paseo 验证宽屏、compact、明暗主题及错误状态。
